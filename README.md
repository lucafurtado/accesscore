# AccessCore

[![CI](https://github.com/lucafurtado/accesscore/actions/workflows/ci.yml/badge.svg)](https://github.com/lucafurtado/accesscore/actions/workflows/ci.yml)

> Enterprise Identity & Access Management platform — JWT auth with rotating refresh tokens, database-resolved RBAC, and an append-only audit trail.

A production-oriented IAM backend and admin console for managing users, roles, granular permissions, and security audit trails. Built end-to-end (API, database, frontend, CI, deployment) as a portfolio project demonstrating how I handle the parts of a system where getting the details wrong has real consequences: token handling, permission boundaries, and tamper-evident audit logging.

## Features

- **Authentication** — JWT access tokens (15 min) + single-use rotating refresh tokens stored server-side (hash only), delivered as an httpOnly cookie the frontend JS never touches
- **RBAC** — `User ─< user_roles >─ Role ─< role_permissions >─ Permission`, permissions resolved from the database on every request (never embedded in the JWT — revoke access and it's gone on the caller's next request, even mid-session)
- **User management** — create, update, activate/deactivate, assign/remove roles, self-disable and self-role-assignment blocked as privilege-escalation guards
- **Audit logging** — every security-relevant action (login, logout, token refresh, password change, user/role/permission CRUD, role assignment) recorded with actor, action, resource, IP, user agent, and a sanitized context payload; the table is append-only at the database level via a Postgres trigger, not just by convention
- **Rate limiting** — login and refresh endpoints throttled per client
- **Security headers, structured logging, request IDs** on every response
- **API-first** — OpenAPI docs auto-generated by FastAPI

## Architecture

```
Next.js 16 (App Router, TypeScript, Tailwind, shadcn/ui)
   │  BFF route handlers hold the refresh-token cookie;
   │  browser JS only ever sees a short-lived access token
   ▼
FastAPI (Python 3.12)
   ├── Routers   → permission-gated via require_permission("resource:action")
   ├── Services  → business rules, domain exceptions
   ├── Repositories → SQLAlchemy 2.0 async, one query concern each
   └── Middleware → request ID, security headers, structured logging
   │
   ▼
PostgreSQL 16
   users · refresh_tokens · roles · permissions · role_permissions ·
   user_roles · audit_logs (append-only, DB-trigger enforced)
```

Router → Service → Repository is the rule everywhere: no route touches a `Session` directly, no service writes a raw query. Permission checks and audit writes both live at the service layer as explicit calls, not inferred from generic request inspection.

## Security

- **Passwords** hashed with bcrypt; never returned in any API response — enforced by tests that assert `hashed_password` never appears in a response body.
- **Refresh tokens** are opaque random values (`secrets.token_urlsafe(32)`); only a SHA-256 hash is persisted. The raw value is visible exactly once, delivered as an httpOnly, `SameSite` cookie — it never reaches frontend JavaScript, so it can't be exfiltrated via an XSS payload reading `document.cookie` or `localStorage`. Rotation is single-use: replaying an already-rotated token fails the same way an unknown one does.
- **Authorization is always server-side.** The frontend's permission checks are UX only — they hide buttons a user can't use. The API re-checks every mutating request against live database state regardless of what the UI shows; verified in [`test_rbac_authorization.py`](backend/tests/integration/api/test_rbac_authorization.py) by calling restricted endpoints directly with a Manager token.
- **Audit logs are append-only at the database level.** A Postgres `BEFORE UPDATE OR DELETE` trigger rejects any mutation on `audit_logs` outright — this holds even if application code had a bug, since the guarantee isn't just "the repository has no `update()` method." A test confirms the trigger itself rejects a direct `UPDATE`.
- **Audit records never contain secrets.** Every write goes through one `AuditService.record()` call site with a typed, primitives-only `context` payload — there's no code path for a raw password, hash, refresh token, or JWT to land in a log row. An acceptance test exercises every audited action and asserts none of those values appear anywhere in the resulting records.
- **401 vs. 403 is a strict contract:** 401 means "I don't know who you are" (missing/expired/invalid token, inactive account); 403 means "I know who you are, and the answer is no." Login failures return the same generic message and status regardless of whether the email exists, preventing account enumeration.
- **Rate limiting** on `/auth/login` and `/auth/refresh` (in-memory, per-client) — the surface that actually matters for brute-force/credential-stuffing, not a blanket global limiter.
- **Security headers** (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Strict-Transport-Security`) on every response; production error responses never leak stack traces (`DEBUG=false`), while `/docs` can still be exposed independently via `ENABLE_API_DOCS` for portfolio review.
- **CORS** locked to the deployed frontend origin in production — no wildcard.

## Deployment

Architecture: **Vercel** (frontend) + **Render** (API, Docker) + **Neon** (Postgres) — all genuinely free, permanent tiers, no credit card required, verified against each provider's official docs. Full step-by-step instructions, including the exact Render dashboard fields and the Neon connection-string rewrite for the async driver, are in [`DEPLOYMENT.md`](DEPLOYMENT.md).

Migrations run as an explicit pre-deploy step (`alembic upgrade head`), never automatically on container boot, so a redeploy can't race two containers' migrations against each other.

**Known trade-off:** Render's free plan sleeps the API after 15 minutes of inactivity; the first request after that takes ~30–60s to cold-start. Expected and acceptable for a portfolio demo, not for a real production SLA.

**Current expected monthly cost: $0.**

## Engineering Decisions & Trade-offs

**Modular monolith over microservices.** Single developer, realistic timeline. Module boundaries (routers/services/repositories per domain) are explicit enough that any of them could be extracted into its own service later without rewriting the domain logic inside it.

**Permissions resolved live from the database, never embedded in the JWT.** Costs one extra query per protected request; buys immediate revocation — a permission or role change takes effect on the very next request, even against a still-valid 15-minute access token. This is verified directly by an integration test that revokes a permission mid-session.

**Refresh tokens in PostgreSQL, not Redis.** A `revoked` flag plus an expiry check on the existing `refresh_tokens` table is sufficient at this scale, and it avoids a second source of truth for session state.

**In-memory rate limiting instead of Redis.** The target deployment is a single Render instance — Redis would add a service, a connection, and a failure mode to manage for a guarantee (shared state across processes) that a single instance doesn't need. A sliding-window counter keyed by client IP, held in process memory, covers the actual threat model (login/refresh brute-forcing) at zero infrastructure cost. The documented trade-off: state resets on redeploy/restart, and it wouldn't be correct across multiple instances — the right call to revisit if this ever needed horizontal scaling, not before.

**HS256 JWT.** Token issuance and verification stay within the same trusted backend process; asymmetric signing matters when external parties verify tokens independently, which doesn't apply here.

**Access token in memory, refresh token in an httpOnly cookie via a BFF.** The browser never has JS-readable access to the refresh token — the one credential that matters most if XSS ever occurs. The access token lives in a JS variable and dies on tab close/reload, capping XSS blast radius at 15 minutes.

## Limitations

- No email verification or password-reset flow — accounts are provisioned directly by an admin.
- No MFA.
- Render's free tier cold-starts after idle (see [Deployment](#deployment)) — not representative of production latency.
- Audit log storage has no retention/partitioning policy yet; fine at demo scale, would need addressing before real production volume.
- Single-tenant — no organization/workspace boundary.
