## Why I Built This

IAM is one of the few domains where getting the details wrong has real consequences — token handling, permission boundaries, and audit trails all have to be correct, not just functional. I built AccessCore to work through those details end to end: a modular FastAPI backend with proper async SQLAlchemy, a real RBAC model instead of a boolean `is_admin` flag, and an audit trail that treats security events as first-class data. It's the kind of system I'd want backing a real internal tool, built to demonstrate how I reason about architecture, security trade-offs, and API design under a realistic timeline.

## Architecture

```
Next.js (TypeScript + Tailwind + shadcn/ui)
          │
          │  HTTPS / REST + JSON
          ▼
     FastAPI (Python 3.12)
     ├── Routers → Services → Repositories → SQLAlchemy ORM
     ├── Core: config, security, dependencies
     └── Middleware: request IDs, structured logging
          │                         │
     PostgreSQL 16               Redis 7
     (primary data store)        (rate limiting)
```

## Tech Stack

**Backend:** Python 3.12, FastAPI 0.115+, SQLAlchemy 2 (async), Alembic, PostgreSQL 16, Redis 7
**Frontend:** Next.js 14+ (App Router), TypeScript, Tailwind CSS, shadcn/ui, Zustand
**Infrastructure:** Docker, Docker Compose, GitHub Actions

## Core Features
- Authentication: JWT access tokens (15 min) + refresh token rotation
- RBAC: granular permission-based authorization (`resource:action` format)
- User Management: full lifecycle — create, edit, deactivate, role assignment
- Audit Logs: automatic trail for all security-relevant actions
- API-first: OpenAPI docs auto-generated by FastAPI

## Engineering Decisions & Trade-offs

**Modular monolith over microservices:** single developer, 7–14 day timeline. Module boundaries are explicit — individual services can be extracted later without rewriting domain logic.

**FastAPI over Django/Flask:** async-first, Pydantic v2 validation built in, automatic OpenAPI docs. Idiomatic for Python API projects in 2024+.

**HS256 JWT:** token issuance and verification remain within the same trusted backend. Asymmetric signing is relevant when external parties verify tokens independently — not applicable here.

**Refresh tokens in PostgreSQL:** eliminates Redis as a second source of truth for token state. A `revoked` flag + expiry check on the existing `refresh_tokens` table is sufficient at this scale.

**Redis only for rate limiting:** every technology in the stack must solve a concrete problem. Redis's atomic TTL-based counters make sliding-window rate limiting clean; the same use case in PostgreSQL would require cleanup jobs.
